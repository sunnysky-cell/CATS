# 更新日志

## 2026-10-09 - 修复 Manager 审批流 500 错误（补齐模板 + Thymeleaf 变量遮蔽 bug）

### 问题现象

- 经理登录后访问 `/manager/pending`、`/manager/applications/{id}`、`/manager/approved-overlapping`、`/manager/history` 全部返回 HTTP 500。
- 员工访问 `/employee/applications/{id}` 详情页部分场景同样 500 或字段渲染为空白。

### 根因分析

1. **模板缺失**：`ManagerCourseController`（提交 519ef7d，标注 untested）返回 `manager/pending` 等 4 个视图名，但仓库中从未提交 `templates/manager/` 目录，导致 `TemplateInputException: Error resolving template [manager/pending]`。
2. **Thymeleaf 保留变量遮蔽**：两个控制器都用 `model.addAttribute("application", ...)` 存放课程申请对象，但 `application` 是 Thymeleaf Web 上下文的内置变量（指向 ServletContext 属性表 `WebEngineContext$ApplicationAttributeMap`），model 中同名属性被完全遮蔽。模板里所有 `${application.*}` 实际取到的是 ServletContext 属性表，因此字段全部渲染为空；`employee/detail.html` 中 `${application.status.name()}` 直接抛 NPE → 500。已用探针测试实证：`${application}` 输出为 `ApplicationAttributeMap@59412c` 而非 CourseApplication。

### 修复内容

- 新增 4 个经理端模板：`templates/manager/pending.html`（待审批列表）、`manager/detail.html`（审批详情 + approve/reject 表单）、`manager/approved-overlapping.html`（同期已批准课程查询）、`manager/history.html`（下属申请历史）。样式与既有 employee/admin 页面保持一致。
- `ManagerCourseController` / `EmployeeCourseController`：model key 由 `application` 改名为 `app`（各 1 行 + 注释说明原因），`manager/detail.html` 与 `employee/detail.html` 同步改用 `${app.*}`。除该改名外未改动队友任何业务逻辑。

### 验证

- 新增回归测试 `ManagerFlowViewTests`（6 个用例）：4 个经理页面渲染、pending 列表包含新申请、detail 页渲染出真实字段内容、approve 带 comment 后状态持久化为 APPROVED。全部通过。
- 全量 `mvn test`：22/22 通过（15 security + 6 manager flow + 1 上下文）。
- 真实服务器 curl E2E 全流程通过：emp1 登录 → 提交申请 → manager 登录 → pending 列表可见 → detail 页字段完整 → 带 CSRF approve → 状态翻转 APPROVED → emp1 详情页正确显示 APPROVED 及 Cancel/Complete 操作区。

### 给队友的提示

- Thymeleaf 模板中禁止使用 `application`、`session`、`param` 作为 model 属性名（保留字遮蔽）。
- 所有含 POST 表单的模板必须使用 `th:action`（而非 `action=`），否则 Spring Security 的 CSRF token 不会注入，提交会 403。

## 2026-10-08 - 课程申请核心 Service 与报销 Service

### 新增功能

- 新增 `CourseApplicationService`，负责课程申请的校验、提交与状态流转（必做功能核心）。
- 新增 `CourseFeeClaimService`，负责课程费用报销的提交与经理审批（选做功能）。
- 申请校验一次返回全部错误，表单可一并显示，员工不必逐条修改重交。

### 后端更新

- `CourseApplicationService.validate(...)` 含 8 项错误检查：结束日期早于开始日期、开始日期非工作日、结束日期非工作日、当年额度未配置、培训天数超年度额度、收费类别未填费用、费用超剩余预算、同期与本人其他 Applied/Updated/Approved 申请重叠；另含 2 项系统处理：按工作日计算培训天数、免费类别费用归零。
- 状态机方法：`submit` / `update` / `delete` / `cancel` / `markCompleted` / `approve` / `reject`，分别由 `checkOwner`、`checkManager`、`checkComment` 把关。
- `validate(...)` 的 `excludeId` 参数使同一方法兼顾新建与编辑：新建传 `null`，编辑传该记录自身 id，避免记录与自身比较导致误判重叠与重复计额度。
- `CourseFeeClaimService.submitClaim(...)` 含 9 项检查：申请不存在、仅限本人申请、免费类别不可报销、课程须为 COMPLETED、一份申请只能报销一次、金额须大于 0、金额不超过课程费、收据文件名必填、结业证书文件名必填。
- 报销 `approve(...)` / `reject(...)` 强制填写经理意见（CA 要求 "manager must again give an appropriate reason"）。
- 报销人 `claimant` 一律取自申请记录本身，不接受前端传入，杜绝替他人提交报销。
- 在 `CourseApplicationRepository` 中补充 `findApprovedOverlapping(...)`，供经理审批页显示同期他人已批准课程（CA 决策支持信息）。
- 在 `CourseApplicationRepository` 中补充 `existsOverlappingApplicationExcluding(...)`，供编辑场景排除自身后判断日期重叠。

### 重构与整合

- 复用队友已有组件，移除本模块中重复实现，`CourseApplicationService` 净减少 117 行。
- 培训天数与工作日判断改为调用 `TrainingDayCalculator`，删除本类中重复的 `CT(...)` 与 `isWorkingDay(...)`。
- 已用天数与已用预算累加改为调用 `EntitlementService.calculateUsedDays(...)` / `calculateUsedBudget(...)`，删除本类中重复的累加循环与 `findActiveApplications(...)`。
- 额度使用汇总 `Summary(...)` 改为委托 `EntitlementService.usageSummary(...)`，删除重复实现。
- 合并 `CourseApplicationRepository` 冲突：保留双方全部查询，每个 `@Query` 与其方法签名一一对应；`findActiveByUserAndYear(...)` 采用队友版本（`int year`），供 `EntitlementService` 与本 Service 共用。

### 缺陷修正

- 修正额度与预算校验误置于累加循环内部的问题：原实现在员工无其他申请时完全跳过校验，且在有多条申请时重复添加同一错误信息；现改为循环外单次判断。
- 修正结束日期工作日校验误判 `start != null` 却检查 `end` 的问题，避免 `end` 为空时抛出空指针异常。
- 修正该校验的错误提示文案由 "Start date" 更正为 "End date"。
- 修正 `checkManager(...)` 中空值检查顺序颠倒的问题，改为先判 `applicant` 与 `manager` 是否为 null 再比较 id。

### 业务规则

- 培训天数由系统按工作日计算，不接受用户填写。
- 起止日期均须为工作日（排除周末与公共假期）。
- 年度培训天数与预算按课程开始日期所属年度核算。
- 免费类别的课程费用强制归零。
- 仅 APPLIED / UPDATED 状态的申请可编辑、可审批；仅 APPROVED 状态可取消或标记完成。
- 报销仅在课程状态为 COMPLETED 且类别需付费时可提交。

### 验证

- `mvn -o clean compile` 全量编译通过（含本次合并进来的 Admin、Training Calendar、Reporting 模块）。

- 在 `CourseApplicationRepository` 中补充 `findByApplicantIdAndYear(...)`，供 `ReportingService` 使用。
- 修正 Training Calendar repository 查询参数绑定，确保 `status`、`monthStart` 与 `monthEnd` 参数正确对应。

- Admin 页面统一加入错误信息显示、表单验证及操作确认。

### 业务规则

- 新建用户时自动建立当年度 Training Entitlement。
- Administrative 用户默认培训天数为 5 天，Professional 用户默认培训天数为 10 天。
- 同一用户同一年度的 Training Entitlement 采用更新或新增逻辑，避免重复记录。
- 用户采用启用/停用方式管理，不直接删除历史用户资料。
- Half-day training 不允许与收费课程类别同时启用。
- 同一天不能重复建立 Public Holiday。
- 非 Admin 用户访问 Admin 路由时会被重定向至 Admin 登录页面。

## 2026-10-06 - Training Calendar 功能

### 新增功能

- 新增 Training Calendar 月度查询功能。
- 所有已登录用户均可查看全体员工的已批准课程。
- 默认显示当前月份的培训安排。
- 支持通过年份和月份下拉框切换月份。
- 支持上一月、当前月和下一月导航。
- 支持跨月和跨年课程查询。
- 显示员工姓名、课程名称、课程类别、培训机构、开始日期和结束日期。
- 无培训记录时显示空结果提示。

### 后端更新

- 在 `CourseApplicationRepository` 中新增培训日历查询方法。
- 查询只返回 `APPROVED` 状态的课程申请。
- 查询使用日期区间重叠规则，确保跨月课程不会遗漏。
- 新增 `CalendarCourseView` 页面数据对象。
- 新增 `TrainingCalendarService`，负责月份校验、日期范围计算和数据转换。
- 新增 `TrainingCalendarController`，负责登录检查、请求参数处理和页面跳转。
- 增加非法年份、非法月份和非数字参数的错误处理。

### 前端更新

- 新增 `training-calendar.html` 页面。
- 新增月度选择表单和月份导航链接。
- 新增 Training Calendar 菜单入口。
- 新增公共 `home.html` 页面，用于登录后的功能导航。

### 登录流程更新

- 登录成功后进入公共 Home 页面。
- Home 页面提供 Training Calendar 入口。
- 保留现有登录、管理员登录和退出登录功能。


### 业务规则

- 只有 `APPROVED` 状态的课程显示在培训日历中。
- 课程只要与所选月份存在日期交集，就会显示在该月份。
- 查询结果面向所有已登录用户，不按员工、经理或角色过滤。
- 培训日历只读数据，不修改课程申请、审批状态或培训额度。
