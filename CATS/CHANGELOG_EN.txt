### 3. Six mandatory CA gaps closed

We checked the Mandatory Features on pages 6 and 7 of `SA63 CA Instructions.pdf` one by one and closed these gaps:

1. **The course must start on a future date** (CA p6: `the course must start on a future date`). `CourseApplicationService.validate()` now rejects a start date of today or earlier and saves nothing. A test submission with `startDate=2026-01-05` was blocked with a message, and the database stayed unchanged.
2. **Half-day granularity for Internal Training** (CA p6: `Half-day sessions are allowed for Internal Training only`; p3: `the granularity is half a day`). `CourseApplication` has a new `boolean halfDay` field (column `half_day bit(1)`). When the box is ticked, `validate()` requires a category with `allowHalfDay` and a single-day course, then counts the course as `0.5` days. `update()` copies the field too. `employee/form.html` has a new checkbox and hint at the end of Course details. Four test cases: internal + half day + one day → saves `training_days=0.5` and `half_day=1`; internal + no half day + one day → `1.0` / `0`; external + half day → rejected; internal + half day + two days → rejected. After approval the CSV report shows `0.5` under `Days Used`, so half days count toward the yearly allowance.
3. **Mark as completed only after the course ends** (CA p6: `Once an approved course has ended, the Employee marks it as attended`). `markCompleted()` now checks the end date after the status check. Completing an APPROVED application that ends in the future (2026-10-23) leaves it APPROVED and tells the employee to wait until the course ends.
4. **Pending list grouped by subordinate name** (CA p7: `This page shows applications grouped by subordinate name`). `ManagerCourseController.pendingApplications()` groups applications in a `LinkedHashMap` (keeping order) and puts it in the model. `manager/pending.html` renders it with two nested `<th:block>` loops; group heading rows use `colspan`, which works with the table search in the teammate's `app.js` (it skips rows with colspan). The group headings render, each employee's rows sit under the right group, and no raw tags leak onto the page.
5. **Approval detail shows the subordinate's days and budget used this year** (CA p7: `the system shows the subordinate's training days and budget used so far this year`). `ManagerCourseController.applicationDetail()` calls `CourseApplicationService.Summary()`, which existed but had no caller. It uses the year of the course start date, the same rule as the allowance check in `validate()`. `manager/detail.html` shows the result after Course fee. A manager opening the detail page sees `Days: 10.0 / 10.0    Budget used: 1533.00 / 2000.00`.
6. **Approved courses in the same period limited to "other direct subordinates"** (CA p7: `lists other subordinates' approved courses during the same course period`). The old `findApprovedOverlapping` query had no ownership filter: it returned courses from the whole organisation, including the applicant's own. The JPQL now adds `ca.applicant.manager.id = :managerId` and `ca.applicant.id <> :excludeApplicantId`, plus ordering. The service and controller signatures follow. `/manager/approved-overlapping` takes a new optional parameter `excludeApplicant` and falls back to `-1` when it is missing, because `<> null` in JPQL is never true. The link in `manager/detail.html` passes the current applicant's id. Excluding emp1 shows only emp2's courses in that period, and the page does not contain emp1's name. Without the parameter the page still returns 200. With an unrelated id the results stay within the manager's own subordinates.

## 2026-10-09 - Fix HTTP 500 in the manager approval flow (missing templates + Thymeleaf variable shadowing)

### Symptoms

- After a manager signed in, `/manager/pending`, `/manager/applications/{id}`, `/manager/approved-overlapping` and `/manager/history` all returned HTTP 500.
- The employee detail page `/employee/applications/{id}` also returned 500 in some cases, or rendered blank fields.

### Root cause

1. **Missing templates**: `ManagerCourseController` (commit 519ef7d, marked untested) returns four view names such as `manager/pending`, but nobody had ever committed a `templates/manager/` folder. Result: `TemplateInputException: Error resolving template [manager/pending]`.
2. **Thymeleaf reserved variable shadowing**: both controllers stored the course application with `model.addAttribute("application", ...)`. `application` is a built-in variable of the Thymeleaf web context (it points to the ServletContext attribute map `WebEngineContext$ApplicationAttributeMap`), so it hid the model attribute of the same name. Every `${application.*}` in the templates read the ServletContext attribute map, so all fields rendered empty, and `${application.status.name()}` in `employee/detail.html` threw an NPE → 500. A probe test confirmed it: `${application}` printed `ApplicationAttributeMap@59412c`, not a CourseApplication.

### Fix

- Added four manager templates: `templates/manager/pending.html` (pending list), `manager/detail.html` (approval detail + approve/reject form), `manager/approved-overlapping.html` (approved courses in the same period) and `manager/history.html` (subordinate application history). They follow the style of the existing employee and admin pages.
- `ManagerCourseController` / `EmployeeCourseController`: renamed the model key from `application` to `app` (one line each, with a comment explaining why), and changed `manager/detail.html` and `employee/detail.html` to use `${app.*}`. Apart from this rename we did not touch any of the teammate's business logic.

### Verification

- New regression test `ManagerFlowViewTests` (6 cases): the four manager pages render, the pending list contains a new application, the detail page renders real field values, and approving with a comment saves the APPROVED status. All pass.
- Full `mvn test`: 22/22 pass (15 security + 6 manager flow + 1 context).
- End-to-end curl run against a real server: emp1 signs in → submits an application → manager signs in → sees it in the pending list → detail page shows all fields → approves with CSRF → status becomes APPROVED → emp1's detail page shows APPROVED and the Cancel/Complete actions.

### Notes for the team

- Do not use `application`, `session` or `param` as model attribute names in Thymeleaf templates (reserved names shadow them).
- Every template with a POST form must use `th:action`, not `action=`. Otherwise Spring Security does not insert the CSRF token and the submit gets 403.

## 2026-10-08 - Core course application service and claim service

### New features

- Added `CourseApplicationService` for validating, submitting and moving course applications through their states (core of the mandatory features).
- Added `CourseFeeClaimService` for submitting course fee claims and manager approval of them (optional feature).
- Application validation returns all errors at once, so the form shows them together and employees do not have to fix and resubmit one error at a time.

### Backend

- `CourseApplicationService.validate(...)` checks 8 errors: end date before start date, start date not a working day, end date not a working day, no allowance set for the year, training days over the yearly allowance, no fee for a fee-paying category, fee over the remaining budget, and overlap with the employee's other Applied/Updated/Approved applications. It also does 2 things on its own: counts training days from working days, and sets the fee to zero for free categories.
- State methods: `submit` / `update` / `delete` / `cancel` / `markCompleted` / `approve` / `reject`, guarded by `checkOwner`, `checkManager` and `checkComment`.
- The `excludeId` parameter of `validate(...)` lets one method serve both create and edit: create passes `null`, edit passes the record's own id, so a record never overlaps with itself or counts its own days twice.
- `CourseFeeClaimService.submitClaim(...)` checks 9 things: the application exists, it belongs to the claimant, the category is not free, the course is COMPLETED, the application has no claim yet, the amount is over 0, the amount does not exceed the course fee, the receipt file name is present, and the certificate file name is present.
- Claim `approve(...)` / `reject(...)` require a manager comment (the CA says "manager must again give an appropriate reason").
- The `claimant` always comes from the application record, never from the form, so nobody can submit a claim for someone else.
- Added `findApprovedOverlapping(...)` to `CourseApplicationRepository`, so the manager's approval page can show other people's approved courses in the same period (decision support required by the CA).
- Added `existsOverlappingApplicationExcluding(...)` to `CourseApplicationRepository` for the overlap check when editing, excluding the record itself.

### Refactoring and integration

- Reused the teammates' existing components and removed duplicate code from this module; `CourseApplicationService` is 117 lines shorter.
- Training days and working-day checks now call `TrainingDayCalculator`; removed the duplicate `CT(...)` and `isWorkingDay(...)` from this class.
- Used days and used budget now come from `EntitlementService.calculateUsedDays(...)` / `calculateUsedBudget(...)`; removed the duplicate loops and `findActiveApplications(...)` from this class.
- The usage summary `Summary(...)` now delegates to `EntitlementService.usageSummary(...)`; removed the duplicate implementation.
- Resolved the `CourseApplicationRepository` merge conflict: kept every query from both sides, with each `@Query` matched to its method signature. `findActiveByUserAndYear(...)` uses the teammate's version (`int year`), shared by `EntitlementService` and this service.

### Bug fixes

- The allowance and budget checks sat inside the summing loop: if the employee had no other applications the checks never ran, and with several applications the same error appeared several times. They now run once after the loop.
- The end-date working-day check tested `start != null` and then checked `end`, which threw a NullPointerException when `end` was empty. Fixed.
- That check's error message said "Start date"; it now says "End date".
- `checkManager(...)` checked for null in the wrong order. It now checks `applicant` and `manager` for null before comparing ids.

### Business rules

- The system counts training days from working days; users do not enter them.
- Start and end dates must both be working days (no weekends or public holidays).
- Yearly training days and budget count toward the year of the course start date.
- Free categories always get a course fee of zero.
- Only APPLIED / UPDATED applications can be edited or decided; only APPROVED applications can be cancelled or marked completed.
- Employees can submit a claim only when the course is COMPLETED and the category charges a fee.

### Verification

- `mvn -o clean compile` passes for the full build (including the Admin, Training Calendar and Reporting modules merged in this change).
